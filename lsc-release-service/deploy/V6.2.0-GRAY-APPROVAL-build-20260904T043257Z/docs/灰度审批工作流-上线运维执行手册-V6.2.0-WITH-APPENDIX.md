### 2. Nacos 配置变更（LSC_GROUP）

在 Nacos Console → `lsc-gateway-routes.yaml` / `lsc-release-service` 应用配置：

```yaml
# ====== [NEW] 灰度审批工作流参数 ======
gray:
  approval:
    default-required-approvals: 2          # 创建审批单默认审批人数（关键动作建议改为3）
    approver-role: ROLE_RELEASE_ADMIN      # 审批人池角色，需与 lsc-user-service 角色中心对齐
    execute-retry-max: 3                   # 自愈任务允许的 EXECUTE_FAILED 自动重试次数
    audit-chain-enabled: false             # 链上存证（金融合规需求时 true）
    stale-executing-seconds: 120           # EXECUTING 超过 2 分钟视为"卡住"，触发回查修复
    self-heal-retry-interval-seconds: 600  # 两次自动重试之间 ≥10 分钟，避免打爆网关
    approver-idle-remind-hours: 24         # 审批人 24h 未处理提醒（下一版提醒任务）

# ====== [NEW] 告警通道（生产切换飞书）======
alert:
  channel: feishu                                    # 默认值 logging，改为 feishu 推送到群
  feishu:
    webhook-url: ${ALERT_FEISHU_WEBHOOK}             # 从 Nacos Secret / 环境变量注入，禁止明文！

# ====== [EXISTING] 保留原 release 配置 ======
release:
  alert-receivers: ${ALERT_RECEIVERS:admin-super-001,admin-super-002}  # 告警接收人 @user_id 列表（英文逗号分隔）
```

⚠️ **Nacos 变更操作顺序**：先 **保存→发布** 配置，再滚动重启服务（服务端 bootstrap 会热拉）；
⚠️ `ALERT_FEISHU_WEBHOOK` 如果走环境变量注入，**不要**在 YAML 明文写死；Nacos Secret 加密配置最佳实践参考 `lsc-common-infra.yaml`。

### 3. XXL-JOB 任务登记（3 个 Handler）

登录 XXL-JOB Admin → 执行器管理 → 选中 `lsc-release-service` → 任务管理 → 新增 3 条：

| JobHandler                  | 调度类型  | Cron               | 运行模式 | 路由策略     | 阻塞处理策略 | 任务描述（建议）                                           | 优先级 |
| --------------------------- | --------- | ------------------ | -------- | ------------ | ------------ | ---------------------------------------------------------- | ------ |
| `grayAuditJob`              | Cron      | `0 0/10 * * * ?`   | Bean     | FIRST        | 单机串行     | Phase P：网关 rollout/status 巡检 + SLO 连续失败/僵尸策略 告警 | P1     |
| `grayApprovalSelfHealJob`   | Cron      | `0 0/5 * * * ?`    | Bean     | FIRST        | 单机串行     | Phase M：EXECUTING 卡死修复 + EXECUTE_FAILED 自动重试       | **P0** |
| `grayStalePolicyEnforceJob` | Cron      | `0 30 3 * * ?`     | Bean     | FIRST        | 单机串行     | Phase P：日度僵尸策略扫描（当前 skeleton，后续版本激活） | P2     |

> **为什么 `FIRST + 单机串行`**：自愈任务会写 DB、调用审批 Service；多实例并发执行会导致同一个 EXECUTE_FAILED flow 被多次 retry。
>
> **为什么阻塞处理=单机串行**：自愈任务最长可能执行 3 分钟（回查 gateway policyStats 有网络 IO），叠加默认 5 min 间隔，避免同一 executor 内新调度线程与上一轮重叠。

## 🟡 冒烟测试用例（5 条 curl + 3 个场景流程）

> 以下命令假设您通过 `lsc-gateway` 路由（推荐生产走网关统一鉴权）。
> 环境变量 `LSC_ADMIN_TOKEN` = 登录后 JWT；`BASE` = `https://admin.lsc.prod.lianshengtong.com`（管理台入口域名）。
> 所有路径前缀与 [GrayApprovalController](file:///workspace/lsc-release-service/src/main/java/com/lianshengtong/release/controller/GrayApprovalController.java) 一致。

```bash
export BASE="https://admin.lsc.prod.lianshengtong.com"
export TOKEN="Bearer <your_admin_jwt>"
export H="Authorization:${TOKEN}"
export CT="Content-Type:application/json"
```

### 冒烟 1：创建审批单（GRADUATE，默认 2 人审批）

```bash
curl -sS -X POST "$BASE/api/release/gray/approvals" \
  -H "$H" -H "$CT" -d '{
  "flowType": "GRADUATE",
  "policyId": "smoke-test-policy-20260904",
  "applicant": "ops_smoke@lianshengtong.com",
  "title": "[SMOKE] 订单服务v2毕业",
  "applyReason": "上线前冒烟测试：错误率达标",
  "requiredApprovals": 2,
  "approvers": ["approver_a@lianshengtong.com","approver_b@lianshengtong.com"]
}' | python3 -m json.tool
# ✅ 校验：
#   code == 0
#   data.status == "PENDING_APPROVAL"
#   data.flowNo 以 "GA20260904" 开头
#   data.requiredApprovals == 2  &&  data.approvedCount == 0
# 👉 记录返回 data.id 为 $FLOW_ID（后续用）
export FLOW_ID="<从data.id取>"
```

---

### 冒烟 2：第 1 人审批通过（approver_a — 1/2 通过，状态仍 PENDING）

```bash
curl -sS -X PUT "$BASE/api/release/gray/approvals/action/approve" \
  -H "$H" -H "$CT" -d "{
  \"flowId\": $FLOW_ID,
  \"approver\": \"approver_a@lianshengtong.com\",
  \"approved\": true,
  \"comment\": \"[SMOKE] 错误率 0.05% < 0.1% 阈值，同意通过\"
}" | python3 -m json.tool
# ✅ 校验：data.approvedCount == 1  &&  data.status == "PENDING_APPROVAL"
# ❌ 常见失败：approver 字段与 JWT 用户不一致 → 检查 JWT 是否对应 approver_a 账号
```

### 冒烟 3：第 2 人审批（approver_b — 2/2 通过 → 触发自动执行网关 graduate）

> 💡 由于 policyId "smoke-test-policy-20260904" **在网关可能不存在**，会走到 fallbackFactory，返回 code=503 fallback。
> 此时审批单状态应为 `EXECUTE_FAILED`（这是**预期行为**，证明 fallback + 状态机正确）。
> 如果网关中真实配置了该策略 → 则直达 `SUCCEEDED`。

```bash
curl -sS -X PUT "$BASE/api/release/gray/approvals/action/approve" \
  -H "$H" -H "$CT" -d "{
  \"flowId\": $FLOW_ID,
  \"approver\": \"approver_b@lianshengtong.com\",
  \"approved\": true,
  \"comment\": \"[SMOKE] 观察期 7 天无事故，同意上线\"
}" | python3 -m json.tool
# ✅ 两种可能都算 PASS：
#    A. 网关有策略 → status == "SUCCEEDED" + executeResponse 包含 graduated:true
#    B. 网关无策略/不可达 → status == "EXECUTE_FAILED" + executeResponse 包含 "fallback"
#       (B 是 fallbackFactory 在生效，证明降级正确；用冒烟 4 再手工重试即可)
```

## 🔵 回滚预案（Rollback Plan — 执行 Step 1 前必须演练一次）

### 分类 A：代码回滚（最常见，10min）

**触发条件**：冒烟测试出现 5xx、Pod 频繁重启、XXL-JOB 连续失败。

```bash
# ===== K8s 回滚 =====
kubectl rollout undo deployment/lsc-release-service -n lsc-production
kubectl rollout status deployment/lsc-release-service -n lsc-production
# ✅ 验证：kubectl get pods -n lsc-production -o wide | grep release-service → 全为老镜像 tag

# ===== VM/systemd 回滚 =====
sudo systemctl stop lsc-release-service
sudo cp /opt/lsc-release-service.jar.bak.v6.1 /opt/lsc-release-service.jar
sudo systemctl start lsc-release-service
```

### 分类 B：配置回滚（Nacos，5min）

**触发条件**：飞书告警刷屏 / SelfHeal 重复推送 P0（阈值过严）。

Nacos Console → `lsc-release-service` 配置 → **历史版本** → 回滚到"上线前版本（YYYYMMDD-HHMM）"。
```yaml
# 紧急临时降级（立刻屏蔽审批路径，不会导致 404，但所有审批行为不再落新表）：
alert.channel: logging          # 静默飞书告警
gray.approval.execute-retry-max: 0  # 彻底停止自愈自动重试
```
> 备注：Nacos 配置热生效，**无需重启 Pod**。

### 分类 C：DDL 回滚（Flyway undo / 手工清理，15min）

**触发条件**：出现锁等待、数据库连接池被 `gray_approval_audit` 批量 insert 打爆（不常见，但预有准备）。

```sql
-- ============== 登录 lsc_release 库 ==============
-- 新表都是 append-only，没有任何外键到老业务表；可以直接 DROP 或 RENAME 保留 7 天

-- 方案 1（保留 7 天数据便于排查，推荐）：
RENAME TABLE gray_approval_flow   TO gray_approval_flow_rollback_20260904;
RENAME TABLE gray_approval_node   TO gray_approval_node_rollback_20260904;
RENAME TABLE gray_approval_audit  TO gray_approval_audit_rollback_20260904;

-- 方案 2（彻底清除）：
DROP TABLE IF EXISTS gray_approval_audit;
DROP TABLE IF EXISTS gray_approval_node;
DROP TABLE IF EXISTS gray_approval_flow;
```

> 若用 Flyway：`flyway undo`（需企业版），或手动 `DELETE FROM flyway_schema_history WHERE version='6.2.0';` 后再 DROP。

### 分类 D：XXL-JOB 任务停用（立即生效，2min）

XXL-JOB Admin → 任务管理 → 搜索 `gray*` → 批量 **停用**（或点"停止"）。
