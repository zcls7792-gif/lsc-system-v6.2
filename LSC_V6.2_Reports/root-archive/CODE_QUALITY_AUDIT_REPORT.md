## 三、代码质量审计结果

### 3.1 已修复BUG清单

#### BUG#1: LogSanitizer类名冲突

- **严重程度**: 中
- **影响范围**: lsc-common 模块
- **文件位置**:
  - `com.lianshengtong.common.utils.LogSanitizer` (功能完整版本)
  - `com.lianshengtong.common.security.LogSanitizer` (功能简陋版本)
- **问题描述**: 两个相同类名的 `LogSanitizer` 类存在于不同包中，其中 `security` 包下的版本功能简陋且未被使用，容易造成开发者混淆和依赖冲突。
- **修复方案**: 将 `security.LogSanitizer` 改为代理模式，转发调用至 `utils.LogSanitizer`，标记为 `@Deprecated`。
- **修复状态**: ✅ 已修复

#### BUG#2: AsyncChainWriter反射修改私有字段

- **严重程度**: 高
- **影响范围**: lsc-evidence-service 模块
- **文件位置**: `AsyncChainWriter.setMaxConcurrent()` 方法
- **问题描述**: 该方法使用 Java 反射修改 `private final Semaphore semaphore` 字段：
  ```java
  Field field = AsyncChainWriter.class.getDeclaredField("semaphore");
  field.setAccessible(true);
  field.set(this, new Semaphore(maxConcurrent));
  ```
  这种做法存在以下问题：
  1. 性能开销大（反射比直接访问慢 10-100 倍）
  2. 在 SecurityManager 受限环境中可能失败
  3. 破坏封装性，难以测试
  4. 代码可读性差
- **修复方案**: 创建 `ConcurrentSemaphore` 内部包装类，通过 `volatile` 语义和同步锁实现线程安全的信号量动态调整。
- **修复状态**: ✅ 已修复

#### BUG#3: 硬编码Redis Key未使用常量

- **严重程度**: 中
- **影响范围**: lsc-evidence-service 模块
- **文件位置**: `EvidenceServiceImpl`、`AsyncChainWriter`
- **问题描述**: 代码中多处直接使用字符串 `"lsc:evidence:pending-count"` 而不是引用 `RedisKeyPrefix.EVIDENCE_PENDING_COUNT` 常量，存在Key命名不一致和维护困难的风险。
- **修复方案**: 将所有硬编码Redis Key替换为 `RedisKeyPrefix` 常量引用。
- **修复状态**: ✅ 已修复

### 3.2 代码质量问题清单

#### 问题#1: 接口与实现类注入混用

- **严重程度**: 低
- **影响范围**: lsc-evidence-service 模块
- **文件位置**: `EvidenceServiceImpl`、`AsyncChainWriter`
- **问题描述**: `EvidenceServiceImpl` 和 `AsyncChainWriter` 直接注入 `SmartContractServiceImpl` 实现类而非 `SmartContractService` 接口。
- **原因**: 需要访问实现类中的特定方法（如 `getCacheHitRate()`、`getAverageLatency()`、`getTotalRpcCalls()`），这些方法未定义在接口中。
- **建议**: 将性能统计方法提取至独立的 `SmartContractMetrics` 接口或 DTO 中。

#### 问题#2: 本地缓存Key硬编码

- **严重程度**: 低
- **影响范围**: lsc-evidence-service 模块
- **文件位置**: `SmartContractServiceImpl`、`AsyncChainWriter`
- **问题描述**: 本地缓存 Key 使用硬编码前缀（如 `"block:"`、`"verify:"`、`"tx:"`、`"record:"`），未统一管理。
- **建议**: 在 `EvidenceLocalCache` 中定义常量类 `CacheKeyPrefix` 统一管理本地缓存 Key 前缀。

#### 问题#3: EvidenceLocalCache使用HashMap而非Caffeine

- **严重程度**: 低
- **影响范围**: lsc-evidence-service 模块
- **文件位置**: `EvidenceLocalCache`
- **问题描述**: 自行实现的本地缓存基于 `ConcurrentHashMap` + TTL，功能相对简单，缺少：
  - 访问频率淘汰策略
  - 权重淘汰
  - 统计信息不够完善
- **建议**: 引入 Caffeine 或 Guava Cache 替换自研缓存实现。

#### 问题#4: 异常处理粒度

- **严重程度**: 低
- **影响范围**: 全项目
- **问题描述**: 部分代码使用了过于宽泛的 `catch(Exception)`，可能掩盖特定异常。
- **建议**: 区分处理业务异常和系统异常，使用自定义异常体系。

#### 问题#5: Test与Main包结构不一致

- **严重程度**: 信息
- **影响范围**: lsc-admin-service 模块
- **问题描述**: admin-service 的测试代码占比仅 17%（main=1,255 vs test=257），远低于项目平均 58.6%。
- **建议**: 补充 admin-service 的 Controller 层和 Service 层测试。
