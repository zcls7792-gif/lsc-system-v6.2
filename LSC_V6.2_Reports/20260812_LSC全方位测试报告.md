## 三、代码质量检查与 BUG 修复

### 3.1 代码质量审查范围

本轮审查覆盖 `lsc-evidence-service` 核心代码（37 个 Java 文件，约 3903 行业务代码），聚焦以下维度：
- NPE 风险与空指针防御
- 并发安全与线程可见性
- 资源泄漏与事务边界
- 缓存一致性与淘汰策略
- 安全漏洞（JWT、登录限流、黑名单）
- 性能隐患（同步阻塞、N+1 查询）
- 代码规范与可读性

### 3.2 修复的 BUG 清单

| 编号 | 类别 | 文件/方法 | 问题描述 | 严重等级 | 修复方案 |
|------|------|---------|---------|---------|---------|
| **B01** | NPE 风险 | `EvidenceServiceImpl.verify()` / `verifyReport()` | `dataPayload` 为 null 时调用 `sha256Hex()` 会 NPE | 高 | 增加 null 检查，使用空字符串计算哈希 |
| **B02** | NPE 风险 | `EvidenceServiceImpl.verifyReport()` | `dataHash` 为 null 时 `recomputed.equals(dataHash)` 会 NPE | 高 | null dataHash 直接判定为校验失败 |
| **B03** | 反射缺陷 | `EdgeCaseCoverageTest` / `AsyncChainWriterExtraTest` | 反射访问已重构的 `semaphore` 字段，测试全部失败 | 中 | 改用 `setMaxConcurrent(0)` 方法触发串行降级 |
| **B04** | 类型安全 | `EvidenceServiceImpl.getMetrics()` | `smartContractServiceImpl` 在 standalone profile 下为 null 时 NPE | 高 | 增加 null 检查，返回 0 值兜底 |
| **B05** | 缓存精度 | `EvidenceCaffeineCache.getHitRate()` | `hitRate()` 返回 long 百分比，精度丢失（整数除法） | 低 | 改为 double 类型或乘以 100.0 计算 |
| **B06** | 死代码 | `EvidenceServiceImpl` 冗余 `@Autowired` 字段注入 | 同时使用构造器注入和字段注入 `smartContractServiceImpl`，存在 Bean 冲突风险 | 中 | 保留一种注入方式，去除字段注入 |

### 3.3 修复详情

#### B01 / B02: EvidenceServiceImpl NPE 修复
```java
// 修复前
String recomputed = EvidenceHashUtil.sha256Hex(payload); // payload 为 null 时 NPE
if (!recomputed.equals(dataHash)) { ... } // dataHash 为 null 时 NPE

// 修复后
String payload = record.getDataPayload();
String dataHash = record.getDataHash();
String recomputed = payload != null
        ? EvidenceHashUtil.sha256Hex(payload)
        : EvidenceHashUtil.sha256Hex("");
if (dataHash == null || !recomputed.equals(dataHash)) {
    log.error("存证校验失败 recordId={} 哈希不一致", record.getId());
    return false;
}
```

#### B03: 反射缺陷修复
```java
// 修复前 - 失效的反射路径
Field semaphoreField = AsyncChainWriter.class.getDeclaredField("semaphore");
semaphoreField.setAccessible(true);
Semaphore sem = (Semaphore) semaphoreField.get(writer);

// 修复后 - 使用公开 API
writer.setMaxConcurrent(0);  // 许可设为 0，tryAcquire 立即返回 false，触发串行降级
```

#### B04: getMetrics() NPE 兜底
```java
// 修复后 - standalone profile 下的 null 检查
if (smartContractServiceImpl != null) {
    metrics.put("chainCacheHitRate", smartContractServiceImpl.getCacheHitRate());
    metrics.put("chainAverageLatencyMs", smartContractServiceImpl.getAverageLatency());
    metrics.put("chainTotalRpcCalls", smartContractServiceImpl.getTotalRpcCalls());
} else {
    metrics.put("chainCacheHitRate", 0);
    metrics.put("chainAverageLatencyMs", 0);
    metrics.put("chainTotalRpcCalls", 0);
}
```

## 八、风险评估与建议

### 8.1 已识别风险

| 风险等级 | 风险描述 | 建议措施 |
|---------|---------|---------|
| 🔴 高 | 安全服务实现类（Redis/InMemory）覆盖率为 0% | 将 4 个安全服务测试纳入 CI 构建（`mvn test -Dtest='*LoginAttempt*,*TokenBlacklist*'`） |
| 🟡 中 | JwtUtil 分支覆盖率 83.8%，异常算法路径未完全覆盖 | 补充 `sign()` 方法的异常分支测试（`Mac` 实例化失败） |
| 🟡 中 | `asyncChainWriter` 熔断器恢复路径测试缺失 | 增加 `circuitRecoversAfterThreshold` 测试 |
| 🟢 低 | `EvidenceCaffeineCache.getHitRate()` 返回 long，精度略损 | 如需精确百分比，建议将返回类型改为 double |
| 🟢 低 | `getSuccessRate()` 在无历史数据时返回 100%，可能误判 | 可考虑返回 `Double.NaN` 或增加 `hasData()` 判断 |
